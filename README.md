## a. Problem Statement

Dry bean producers and seed-certification labs need an automated way to sort
harvested grains into their registered varieties for quality control and
market pricing, instead of relying on manual visual inspection. This project
treats variety identification as a **multiclass classification problem**:
given 16 geometric measurements extracted from a photograph of a single dry
bean grain, predict which one of seven registered varieties it belongs to.
Five classical machine learning classifiers are trained on the same data
split and compared on six evaluation metrics, and the best model is served
through an interactive Streamlit web application.

## b. Dataset Description

**Dataset:** UCI Machine Learning Repository - Dry Bean Dataset (id 602)
**Link:** https://archive.ics.uci.edu/dataset/602/dry+bean+dataset

**Citation:**
> Koklu, M. and Ozkan, I.A. (2020). *Multiclass Classification of Dry Beans
> Using Computer Vision and Machine Learning Techniques.* Computers and
> Electronics in Agriculture, 174, 105507.
> https://doi.org/10.1016/j.compag.2020.105507

Images of 13,611 grains from 7 registered dry bean varieties were captured
with a high-resolution camera; a computer vision pipeline segmented each
grain and extracted 16 geometric features (12 dimensional measurements + 4
derived shape factors) per grain.

| Property | Value |
|---|---|
| Instances (raw / after de-duplication) | 13,611 / 13,543 |
| Features | 16, all numeric |
| Target | `Class` (7 categories: Barbunya, Bombay, Cali, Dermason, Horoz, Seker, Sira) |
| Missing values | None |
| Exact duplicate rows removed | 68 |

See [`data/README.md`](data/README.md) for the full feature list and file
layout.

### Preprocessing

1. Load the official `.xlsx` release and drop exact duplicate rows (68 removed, reported above).
2. Confirm there are no missing values (none found; the pipeline raises an error rather than silently imputing if this were ever to change).
3. Separate the 16 feature columns from the `Class` target column.
4. Encode `Class` with `LabelEncoder` (needed for `roc_auc_score`/`matthews_corrcoef`, which require numeric labels); human-readable class names are restored everywhere in the UI and reports via `inverse_transform`.
5. **Stratified** 80/20 train/test split (`random_state=42`), so the class distribution is preserved in both partitions and every model is compared on the *same* split.
6. All preprocessing (in particular, `StandardScaler` for Logistic Regression and kNN) is fit **only on the training fold**, inside a scikit-learn `Pipeline`, to prevent test-set leakage. Decision Tree, Naive Bayes and Random Forest do not need scaling and are trained on the raw numeric features.
7. The labelled 20% test split is saved as [`test_data.csv`](test_data.csv) and used by the Streamlit app for on-demand evaluation.

## d. Models Used

All five models below were trained on the **identical** stratified 80/20 split
(`random_state=42`) and evaluated on the same held-out test set (2,709 rows).

- **AUC** is macro-averaged, one-vs-rest, computed from predicted class
  **probabilities** (never from hard predicted labels) - required because
  this is a 7-class multiclass problem.
- **Precision / Recall / F1** use **weighted** averaging, so the class
  imbalance in the dataset (Bombay: 522 samples vs. Dermason: 3,546) is
  reflected in the headline numbers. Full per-class breakdowns are available
  in the Streamlit app's Classification Report view.
- Hyperparameters: Logistic Regression, Decision Tree and Random Forest use
  `class_weight="balanced"` to counter class imbalance (Naive Bayes and kNN
  do not support this parameter). kNN's `n_neighbors` was selected via 5-fold
  stratified cross-validation on the **training set only** (grid
  `{3,5,7,9,11}`, scored on weighted F1) - it never touched the test set
  during tuning. Full parameter choices are documented in
  [`src/train_models.py`](src/train_models.py).

### Model Observations

*(Full detailed discussion, including per-class F1 and train/test accuracy gaps, is in [`artifacts/model_observations.md`](artifacts/model_observations.md).)*

| ML Model Name | Observation about model performance |
|---|---|
| Logistic Regression | Second-highest AUC (0.9945, best of all 5) and smallest train/test accuracy gap (0.9213 vs 0.9147 = 0.0066) among the strong performers - generalizes well and stays interpretable, but its linear boundary limits it on the hardest class (Sira, F1 0.867). |
| Decision Tree | Weakest of the four non-Bayes models (Accuracy 0.8981). Even with `max_depth=10` and `min_samples_leaf=5` capping complexity, it shows the largest train/test gap among non-ensemble models (0.9433 vs 0.8981, 4.5 points) - a single tree overfits faster than it generalizes here. Most interpretable (readable if/else path) and fastest to train/score. |
| kNN | k=9 selected via 5-fold CV on the training data only. Competitive accuracy (0.9129) and AUC (0.987), moderate train/test gap (2.4 points). Main drawback: it must store and scan the full training set (10,834 rows) at inference time, making it the slowest to score and by far the largest saved model file among the non-ensemble models. |
| Naive Bayes | Clearly weakest overall (Accuracy 0.7630, MCC 0.7143). Worst per-class F1 on Barbunya (0.548) and Seker (0.683), whose geometric features are strongly correlated - a direct violation of the conditional-independence assumption Naive Bayes relies on. Near-zero train/test gap (0.0008) shows it is *underfitting*, not overfitting. |
| Random Forest (Ensemble) | Best or tied-best on 5 of 6 metrics (Accuracy 0.9188, Precision/Recall/F1 ~0.9187-0.9188, MCC 0.9017); only 0.0013 behind Logistic Regression on AUC. Individual trees fit the training data perfectly (train accuracy 1.0000, an 8.1-point gap down to test), but bagging 300 trees still generalizes best of all five models. Its only recurring weakness (shared by every model tested) is confusing Sira with Dermason (57 of 527 Sira grains). |
| **Overall Winner for this dataset** | **Random Forest (Ensemble)** - chosen because it leads on 5 of the 6 metrics (not just accuracy), and its one shortfall (AUC) trails the leader by a negligible 0.0013. The trade-off is a larger model file (~10.8 MB vs a few KB for the linear/tree/Bayes models) and lower interpretability than a single Decision Tree or Logistic Regression. |

## Streamlit Application Features

- **Overview** page: problem statement, dataset summary, source/citation, class-distribution chart.
- **Predict & Evaluate** page:
  - Model-selection dropdown (choose any of the 5 trained models).
  - CSV upload for test data, with a **download button for a correctly formatted sample CSV**.
  - Validation with clear error messages for missing feature columns, non-numeric values, and unexpected/extra columns (which are ignored with a notice rather than failing).
  - Predictions shown with human-readable class labels, downloadable as CSV.
  - If the uploaded CSV includes a `Class` column: live evaluation metric cards (all 6 metrics), a confusion matrix heatmap, and a full per-class classification report - all computed on that specific upload.
  - If `Class` is absent: predictions are still shown, with an explicit message that metrics require ground-truth labels.
- **Model Comparison** page: the full comparison table (best value per metric highlighted), an accuracy bar chart, and the detailed written observations.
- **About This Project** page: assignment context and an academic-integrity statement.

Models are loaded once via `st.cache_resource` and are **never retrained inside the deployed app** - `app.py` only loads the `.joblib` artifacts produced by `src/train_models.py`.

## Limitations

- The Streamlit Community Cloud free tier has limited memory/CPU, which is
  why only the 20% test split (not the full 13,543-row dataset) is uploaded
  for on-demand evaluation in the app.
- The dataset is imbalanced (Bombay is ~15% the size of Dermason); this is
  partially mitigated with `class_weight="balanced"` where supported, but
  minority-class metrics (see the Classification Report in the app) are
  still noisier than majority-class metrics.
- All five models were trained once with the documented hyperparameters
  (plus light CV-based tuning for kNN's `k`); an exhaustive hyperparameter
  search was intentionally not performed, to keep training fast and
  reproducible for grading.
